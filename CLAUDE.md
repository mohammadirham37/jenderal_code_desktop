# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

JenderalCode Desktop: a Tauri 2 desktop AI coding agent (Rust backend + React/TypeScript frontend). The spec is `JenderalCode-Desktop-PRD.md`. Code comments and docs reference PRD sections (`FR-xx`, `§n`). `README.md` and `docs/ARCHITECTURE.md` are written in Indonesian; `docs/ARCHITECTURE.md` maps the implementation to the PRD and is the best single overview.

## Commands

```bash
# Rust (Cargo workspace at repo root)
cargo test --workspace                       # all unit + integration tests
cargo test -p jcode-permissions              # one crate (crate names are jcode-<dir>)
cargo test -p jcode-storage migrations_are_idempotent   # one test
cargo test -p jcode-e2e-tests                # cross-crate e2e (tests/e2e/tests/e2e.rs)

# Frontend (frontend/)
cd frontend && npm install
npm run build        # tsc --noEmit + vite build; this is the frontend's only check (no test script)

# App (run from repo root or apps/desktop)
npx --yes @tauri-apps/cli@2 dev              # starts vite on :5173 + Tauri
npx --yes @tauri-apps/cli@2 build            # release bundle -> target/release/bundle/
npx --yes @tauri-apps/cli@2 build --bundles app   # skip DMG if Finder AppleEvent times out
```

`tauri.conf.json` locates `frontend/` by walking up from the cwd, so `tauri dev/build` works from the root or `apps/desktop`.

Releases for macOS, Linux and Windows: follow `docs/RELEASE.md` (Linux/Windows via `scripts/release/` in Docker, macOS universal on a Mac). This repo is public: never commit credentials, SSH hosts/users/IPs, or local/remote folder paths. Use placeholders such as `<build-host>`.

## Architecture

Workspace layout: `apps/desktop` (Tauri shell), `crates/*` (libraries, all named `jcode-*`), `frontend/` (React 19 + Vite + Tailwind 4 + zustand), `tests/e2e`.

**Agent turn flow** (the core loop, spread over several crates):
1. Frontend calls `invoke("send_message")` → `apps/desktop/src/commands.rs`.
2. `AgentRuntime::send_message` (`crates/agent-runtime/src/lib.rs`) spawns a tokio task per turn. `context.rs` builds the system prompt from the profile, file tree, git status, and project instruction files (marked UNTRUSTED).
3. `create_provider` dispatches on `ProviderKind` to an `AiProvider` impl (`provider-openai` / `-anthropic` / `-google` / `provider-core::mock`). `stream()` yields `StreamEvent`s (TextDelta, ToolCall*, Usage, Done).
4. For each tool call, `agent-runtime/src/executor.rs`: `classify` → `permissions::Action` → `PolicyEngine::check` (Allowed / Denied / NeedsApproval). NeedsApproval persists an approval, emits `chat://approval`, and waits on a oneshot resolved by the `decide_approval` command. Then `execute` runs the tool, snapshotting files to a checkpoint (`tool-filesystem::CheckpointStore`) before any write or delete.
5. Loop until no tool calls, the iteration limit, or cancellation.

Runtime events go through the `EventSink` trait (agent-runtime). `apps/desktop/src/sink.rs` (`TauriEventSink`) turns them into Tauri events: `chat://*`, `terminal://*`, `fs://changed`. Tests use `NoopSink` or custom sinks with the mock provider, so you can exercise the full approval flow without network.

**Cross-cutting conventions**
- Shared types (`ChatMessage`, `ToolSpec`, `StreamEvent`, provider/model configs, events) live in `crates/common`. `frontend/src/lib/ipc.ts` mirrors them by hand, plus every command signature. Changing a serialized Rust type or command means updating `ipc.ts` too.
- New Tauri command: implement it in `apps/desktop/src/commands.rs`, register it in `generate_handler![...]` in `apps/desktop/src/main.rs`, and add a typed wrapper in `ipc.ts`.
- Confirmations: `await confirmAction(...)` (`frontend/src/lib/confirm.ts`), never `window.confirm`. The dialog plugin replaces `window.confirm` with an async function, so its Promise is always truthy and the action runs without waiting.
- New agent tool: add its spec in `executor::tool_specs`, its permission mapping in `executor::classify`, and its execution in `executor::execute`. Agent modes (Plan/Build/Review) are enforced twice: tools are filtered out of the specs sent to the model, and they are rejected again at execution time. Keep both in sync.
- Storage: a single SQLite connection behind a mutex (`crates/storage`). Migrations are SQL files in `crates/storage/migrations/` registered in the `MIGRATIONS` list via `include_str!` and tracked in a `_migrations` table. Add new numbered files; never edit applied ones. `foreign_keys` is ON and sessions/messages cascade from `workspaces`, so "Remove from list" hides a project (`workspaces.hidden`, `Db::hide_workspace`; reopening the folder unhides it) instead of deleting the row.
- Provider adapters must report unknown model capabilities as `None` rather than guessing. All OpenAI-compatible vendors (OpenAI, DeepSeek, Mistral, xAI, Groq, Ollama, LM Studio) share `provider-openai`; URL presets live in `provider-core::provider_presets()`.
- API keys never go in the DB, only a credential reference. `provider-core/src/credentials.rs` supports a 0600 file backend (default) and the OS keychain, with migration between them.

**Security choke points** (keep changes routed through these):
- Path resolution: `tool-filesystem` `Workspace::resolve` (canonicalize + containment, rejects symlink escape).
- `permissions`: `is_sensitive_path`; `assess_command` tokenizes shell commands (splits on `; | & && ||`, follows `$(…)`, backticks, `bash -c`, skips wrappers and git global options) and feeds `is_catastrophic_command` (absolute deny) and `is_git_remote_command` (always asks). Balanced asks for every command; Yolo (full access) never prompts: it allows everything except the catastrophic deny-list and writes outside the workspace. Add new rules there with a test, not via substring checks.
- `tool-filesystem`: `edit.rs::plan_edit` is the single matcher for `fs_edit` (execution and approval preview): exact, then CRLF-, trailing-whitespace-, indentation- (re-indents `new_string`) and quote-tolerant tiers; relaxed tiers only apply to a unique match, and the not-found error shows the most similar region with line numbers. `write_no_follow` (O_NOFOLLOW) for all writes; `search`/`glob_files` skip symlinks and `is_sensitive_name` files. Read-only git calls run with `core.fsmonitor=false` and `core.hooksPath` disabled.
- Agent command execution: `tool-terminal::run_exec` (timeout, output cap, process-group kill). This is separate from the interactive human PTY in `apps/desktop/src/terminal.rs` (portable-pty → xterm.js).

`apps/desktop/src/watcher.rs` watches the workspace with `notify` (trailing 300 ms debounce, ignores `.git`/`target`/`node_modules`/build dirs) and emits `fs://changed`.

**Desktop shell rules**: Tauri commands doing IO or spawning processes are `async` and run their body in `spawn_blocking` (sync commands run on the UI thread). The webview has a strict CSP (`tauri.conf.json`) and a navigation lock in `main.rs`, so model output can never load remote resources or navigate away; the chat markdown renderer also blocks images and link navigation. `TauriEventSink` coalesces `chat://delta` events (~30 ms) and flushes before any other event for the session.

**Browser preview** (`apps/desktop/src/browser.rs`, `frontend/src/features/browser/BrowserPanel.tsx`): a native child webview (`preview-<id>`, tauri `unstable` feature) laid over a placeholder div; the panel polls its rect each frame and sends logical bounds (CSS px × app zoom), hiding the webview when the placeholder is hidden or the command palette is open (native webviews always paint above HTML). Previews are incognito, may only navigate to http(s) and never to the app's own origins, and get no IPC: the capability in `capabilities/default.json` is scoped to `webviews: ["main"]`. The navigation-guard plugin in `main.rs` dispatches on the webview label.

**Centre tabs (Chat layout)**: `features/workspace/CenterColumn.tsx` puts a tab strip over the chat column: the permanent Chat tab plus terminal and agent-CLI tabs (state in `stores/centerTabs.ts`). Agent tabs call `terminal_create` with a `command`, which `terminal.rs::build_command` runs as `$SHELL -l -i -c <command>` (`bash -i` on Linux: a login bash skips `~/.bashrc` when `~/.bash_profile` exists; all shell spawns use `tool-terminal::user_path::interactive_shell_args`); presets live in `AppSettings.agent_clis` (user-editable, never model output; new presets reach saved lists via a settings migration, see `007_antigravity_agent.sql`; `bypass_args` holds the CLI's skip-permissions flags, appended only when the user picks "bypass" in the menu, and such tabs get a red ShieldOff icon; `install_command` holds the official installer from `common::default_install_command`, per platform (PowerShell syntax on Windows), filled into saved lists by `018_agent_install_commands.sql` via the `@AGENT_INSTALL_COMMANDS@` placeholder; npm ones go through `npm_global_install`, which falls back to `sudo` when npm's global folder is not writable), and `agent_detect.rs` checks the login-shell PATH for the "+" menu. An agent that is not found gets an "install" button there: after `confirmAction` shows the command it runs in an `install` tab (never saved or restored), whose exit re-runs detection. xterm instances live in `features/terminal/xtermRegistry.ts`, outside React, so tabs keep their scrollback across page/layout switches; centre tabs belong to their project: switching projects parks them (`centerTabs.parked`; processes keep running, output keeps landing in the registry) and switching back restores them; they are killed only when closed, when their project is closed or removed from the list (`onWorkspaceRemoved`), or on quit. The project list shows a badge for parked projects with live tabs. The tab lists are saved in localStorage (`jcode:center-tabs`); after a restart a project's tabs are respawned the first time it is shown, agent tabs with the preset's `resume_args` (`claude --continue`, `codex resume --last`, `opencode`/`agy`/`cmd --continue`; new presets reach saved lists via `013_agent_resume_args.sql`, or with the preset's own migration such as `016_commandcode_agent.sql`; Command Code's program is `cmd`, `cmdc` on Windows (`COMMAND_CODE_BIN`, filled into migration SQL for `@COMMAND_CODE_BIN@`)) placed before the bypass flags, while Restart uses the plain command. The last open project (`jcode:last-workspace`) reopens at startup and each project's last session (`jcode:last-session:<id>`) is selected again once `useChat().sessionsLoaded`. Terminals and the Git panel follow the app theme: the registry has `DARK`/`LIGHT` xterm palettes (light raises `minimumContrastRatio` so CLI colours meant for dark terminals stay readable) and re-themes every terminal when the `dark` class on `<html>` changes; panels use light/`dark:` variants, never a forced dark background. The registry resolves `--font-mono` to a literal stack and opens terminals only after IBM Plex Mono loads (xterm measures with canvas, where CSS variables do not work). This is unrelated to `crates/agent-cli` (one-shot non-interactive runs).

**Agent CLI usage** (`apps/desktop/src/agent_usage/`, `features/workspace/AgentUsage.tsx`): the Gauge button in the centre tab strip calls `agent_usage`, which builds one `AgentUsageReport` per CLI. Claude Code: OAuth usage endpoint with the token from the Keychain item `Claude Code-credentials` (or `~/.claude/.credentials.json`); read-only, never refreshed, sent only to api.anthropic.com. Codex: live from `chatgpt.com/backend-api/wham/usage` with `~/.codex/auth.json` tokens (never refreshed), falling back to the newest `rate_limits` per `limit_id` in `~/.codex/sessions/**/*.jsonl`. Antigravity: `agy -p /usage --output-format json` (a slash command, no model turn; skipped for agy < 1.1.11, which would treat it as a prompt). OpenCode: 5 h / 7 d token and cost totals from `opencode.db` (read-only). Agent detection (`agent_detect.rs`) uses `$SHELL -l -i` so PATH entries from `~/.zshrc` count.

**Agent context and reasoning**: the profile-independent working guidelines live in `context.rs::WORKING_GUIDELINES` (built-in profiles are seeded into the DB once, so edits to their prompts do not reach existing users). `prepare_history` keeps the newest tool results whole up to `PROTECTED_TOOL_CHARS` and shortens older ones, and drops `reasoning` before the last user message. Reasoning from OpenAI-compatible providers (`reasoning_content` / `reasoning`) arrives as `StreamEvent::ReasoningDelta`, is stored in `messages.reasoning`, streamed as `chat://delta` with `reasoning: true`, and sent back as `reasoning_content` for the turn in progress. `fs_read` returns `cat -n` numbered lines (offset/limit); `fs_edit` strips copied line-number prefixes. Agent commands get the login-shell PATH via `tool-terminal::user_path` (resolved in a background thread at startup).

**Agent tools beyond fs/git/terminal**: `web_fetch` (`agent-runtime/src/web.rs`, permission action `FetchUrl`, grant `fetch_urls`; asks unless Yolo or granted), `todo_write` (`todo.rs`; the list lives in the call args and the chat renders it in `ToolRunCard`), `fs_multi_edit` (all-or-nothing, via `plan_edit`). Consecutive calls of `executor::is_parallel_safe` tools run concurrently in `run_turn`; results are still persisted in call order. Built-in Plan/Review allowlists live in the DB, so new read-only tools need a migration (see `009_profile_new_tools.sql`).

**Reliability guards**: `retry.rs` reopens the model stream on transient errors (429/5xx/network, ~1 min backoff; 4xx auth/request errors fail at once). A connection that breaks mid-response (e.g. reqwest's "error decoding response body") reaches the runtime as `StreamEvent::Error` (adapters never put it in the text): `run_turn` drops the partial step (tools only run after the stream) and asks again with the same history on the same backoff, the sub-agent loop likewise; after the last attempt the partial text is kept and `chat://error` reports it. The chat store clears an unsaved `streaming` bubble when the status returns to `thinking`. `executor::FileTracker` (per session, in `SessionHandle`) records each file's size+mtime when the agent reads or writes it; `fs_edit`/`fs_multi_edit`/`fs_write` refuse existing files that were not read in the session or changed since. `fs_read` appends `AGENTS.md`/`CLAUDE.md` from subdirectories (once per session); the user's global `~/.config/jenderalcode/AGENTS.md` goes into the system prompt. Command output keeps head and tail (`tool-terminal::HeadTail`, `truncate_middle_for_model`).

**LSP diagnostics** (`crates/tool-lsp`): after `fs_write`/`fs_edit`/`fs_multi_edit`, `executor::with_diagnostics` asks `LspManager` (owned by `AgentRuntime`, one server per root + language, started in the background on first use) for the file's diagnostics and appends the errors to the tool result. Servers: vtsls (TS/JS; bundles TypeScript), intelephense (PHP), pyright, rust-analyzer, gopls, from the login-shell PATH or via `npx` when `lsp_auto_download` is on. Live checks: `cargo test -p jcode-tool-lsp live_ -- --ignored`.

**Sub-agents** (`agent-runtime/src/subagent.rs`): the `task` tool runs a read-only sub-agent loop (same model, `SUBAGENT_TOOLS` only, own `FileTracker`, no LSP, max 30 steps) and returns just its final report; `process_call` routes `task` there before permission classification. Anything that would need approval is refused inside sub-agents. `TurnEnv` carries the provider/model/system prompt into tool handling.

**Skills** (`agent-runtime/src/skills.rs`, `features/settings/SkillsSettings.tsx`, composer `/` menu in `ChatPanel.tsx`): `SKILL.md` folders from the project (`.agents/skills`, `.claude/skills`, `.opencode/skills`) and global dirs (`~/.agents/skills` first, then `~/.config/jenderalcode/skills`, `~/.claude/skills`, `~/.config/opencode/skills`, `~/.codex/skills`); first name wins, `disabled_skills` hides them. Names and descriptions go into the system prompt; the `skill` tool loads one (or a file of it). A user message `/name …` is stored with the skill text attached (`expand_slash_command`), and the chat renders it back as `/name request`. Installing/removing runs `npx skills add|remove … -g` (`-a universal`) after validating names for the shell.

**MCP servers** (`crates/tool-mcp`, `agent-runtime/src/mcp.rs`, `features/settings/McpSettings.tsx`): a hand-rolled MCP client (stdio, newline-delimited JSON-RPC, login-shell PATH, scrubbed env, own process group; streamable HTTP with JSON or SSE replies and `Mcp-Session-Id`; legacy SSE is reported as unsupported). Config uses the `.mcp.json` format: global servers in `~/.config/jenderalcode/mcp.json` (0600), project servers from `<root>/.mcp.json` only after the user trusts that exact file (`AppSettings.mcp_trusted_projects`, FNV-1a fingerprint as hex; an edited file needs trust again); `disabled_mcp_servers` hides servers by name. `McpManager` (owned by `AgentRuntime`) keeps one server per canonical root + name and restarts it when its config changes; `run_turn` syncs it at turn start (cancellable) and offers tools as `mcp__<server>__<tool>` (≤64 chars), plus the servers' `instructions` in the system prompt. Permission action `McpTool` asks unless Yolo or grant `mcp_tools`; MCP tools are not read-only (excluded from Plan/Review), and an allowlist enables them with `mcp` or `mcp__<server>`. Image results are named, not passed on. Live check: `cargo test -p jcode-tool-mcp live_ -- --ignored`.

**Composer mentions and images**: `@query` lists project files from `fs_find_files` (`Workspace::find_files`: gitignore-aware, no symlinks or `is_sensitive_name` files, ranked name > path > subsequence); picking one writes `@path` and adds it to the attachments, which `context::pack_attachments` appends after `--- Attached files ---` (the chat shows those as chips; keep `ATTACHED_MARKER` in `ChatPanel.tsx` in sync). The paperclip's file dialog goes through `resolve_picked_attachments` (`commands::sort_picked`: containment via `Workspace::resolve` on canonical paths, so symlinked or differently-cased paths still count as inside; images from outside the project come back as pixels, ≤20 MB; any other file is typed into the message as its path). Files dropped from the OS take the same route (`ChatPanel` `attachPaths`): Tauri's native `onDragDropEvent` gives paths in physical px, divided by `scaleFactor × zoom` to hit-test the composer; HTML drop events never see OS files. Pasted images are scaled to ≤1568 px (`lib/images.ts`) and sent as `ImageAttachment { mime, data }` (base64) on `ChatMessage`/`MessageRecord.images` (`messages.images_json`). `send_message` refuses them when the model's `vision` is `Some(false)` (unknown is allowed) and checks count/type/size (`check_images`); adapters send OpenAI `image_url` data URLs, Anthropic base64 `image` blocks, Google `inlineData`. Context budgets count an image as `IMAGE_CHARS`. Messages with files or images can be queued but not used to steer. Quick Open (`components/QuickOpen.tsx`, ⌘P / Ctrl+P, `useApp().quickOpen`) uses the same `fs_find_files` and opens the pick in the editor (`useEditor().revealTick` lets Chat layout reveal an already-active file); Ctrl+P is left to terminals outside macOS.

**Enhance prompt** (`agent-runtime/src/enhance.rs`, composer PenLine button / ⌘⇧E, phone `chat.enhance`): one tool-less call to the session's model with `ENHANCE_INSTRUCTIONS` (keep intent and details, no invented facts, same language, prompt only), the project name and the last 6 user/agent turns; `clean_reply` strips fences, quotes and "Here is…" lines; only token usage is stored and the draft is replaced in the composer with Undo.

**Compaction**: at the start of a turn, `context::compaction_split` checks whether the history is over 80% of the budget with earlier turns making up a real share; `AgentRuntime::summarize` then asks the session's model for a summary, persisted as a user message starting with `COMPACTION_MARKER` (dated 1 ms before the triggering request). `trim_to_last_compaction` drops everything before the newest summary when loading history, and `merge_consecutive_user_messages` joins it with the request. Keep the marker in sync with `ChatPanel.tsx`.

**Turn limits**: `run_turn` pauses (persists an assistant note starting with `PAUSE_MARKER`, no error event) when `max_iterations` (default 100) is reached or the same tool call fails `REPEATED_FAILURE_LIMIT` times in a row; the chat renders it as a card with a Continue button. Keep `PAUSE_MARKER` in sync with `ChatPanel.tsx`.

**Queue and steer**: while a turn runs, the composer's Enter queues the message (`useChat().queued`, per session, sent by `turnEnded` on the next idle status; held after Stop or an error) and ⌘/Ctrl+Enter steers: `steer_message` → `AgentRuntime::steer` pushes it onto `SessionHandle.steer`, and `run_turn` persists it as a user message after the step's tool results (or right after a final answer, continuing the turn). `BusyGuard` clears unused steering with `busy`; the frontend moves those back into the queue. Anthropic/Google adapters merge a user message into the preceding tool-result turn.

**Remote control** (`crates/remote`, `apps/desktop/src/remote.rs`, `features/settings/RemoteSettings.tsx`; spec `docs/REMOTE_PROTOCOL.md`, shared with the Go relay `jenderalcode_backend` and the Flutter app `jenderalcode_mobile`, which live outside this repo): a phone drives sessions through an untrusted relay. Both ends connect out over WebSocket; app messages are end-to-end encrypted (X25519 static keys, HKDF per direction, XChaCha20-Poly1305, ±60 s skew + replay guard; `docs/remote-test-vectors.json` is checked by `cargo test -p jcode-remote` and must stay identical for the Dart client). Pairing: QR (`jcode://pair`) → phone claims and approves on the relay → the desktop shows the 6-digit SAS and only stores the phone (`remote_peers`, migration 015) after the user allows it; `PeerBook` drops everything from other devices. The X25519 secret (`remote:key`) and the relay registration (`remote:device`, tied to the relay URL; changing the URL forgets phones) live in the credential store. `RemoteController` is both the request dispatcher (methods in spec §6.2) and an `EventSink`: `sink::FanoutSink` sends runtime events to the webview and to phones subscribed to that session (deltas coalesced at 100 ms). The relay is fixed (`remote::RELAY_URL`, the official `https://backendcode.jenderalcorp.com`; not user-editable). Rules: `remote_enabled` off by default; `remote_allow_full_access` (off by default, reported to phones as `capabilities`) gates Yolo (`session.set_policy`, and `chat.send`/`chat.steer` into Yolo sessions → `yolo_blocked` otherwise), terminals and every write (`fs.write/create/delete/rename`, `git.stage/unstage/discard/commit/checkout/create_branch`, `checkpoints.restore`) → `not_allowed`; turning it off detaches phones from terminals and kills terminals they opened. Remote approvals never create grants; new sessions from the phone copy the project's latest session's model and never start in Yolo. Files/git/agents/models/skills handlers live in `remote_ops.rs` (blocking, scoped to the request's `workspace_id`; secret-like files refused). Terminals (§6.5): `TerminalManager` keeps title/kind/origin and a 128 KiB scrollback per PTY and calls an observer (`set_observer`) that `RemoteController` uses to stream `terminal.data` (50 ms batches) to attached phones; desktop tabs pass their label via `terminal_create`'s `title`, phone-opened terminals (`origin: remote`, max 6) also appear as centre tabs of their project (`remote://terminal` → `useCenterTabs().adoptRemote`, Smartphone icon; `xtermRegistry.joinXterm` replays `terminal_snapshot` and drops data events with `seq` ≤ the snapshot's, so nothing is lost or repeated). Those tabs keep the phone's PTY size (`fixed`, following `terminal://resized`) until restarted on the desktop. Only phone-opened terminals can be resized/closed from the phone. Phone browser (§6.10, `remote_http.rs`): `http.request`/`http.read` fetch **loopback-only** URLs (`remote_http::loopback_url`; redirects passed back, `Accept-Encoding: identity`, bodies chunked at 384 KiB and kept 120 s) for the phone's WebView, whose local proxy (`features/browser/browser_proxy.dart`) binds the target's port on the phone's 127.0.0.1; `browser.targets` lists the desktop previews' localhost URLs; capability `browser` follows the same setting; no WebSocket/HMR yet. The Android app comes from the GitHub releases of `jenderalcode_mobile`, which always carry a stable `JenderalCode-Mobile.apk` asset: Settings (and the pairing dialog) show a QR of `remote::MOBILE_APK_URL` (`releases/latest/download/JenderalCode-Mobile.apk`, one scan downloads the APK), and `remote_open_mobile_download` opens the fixed `MOBILE_DOWNLOAD_URL` page in the system browser (it takes no URL argument; the webview itself never navigates). The phone app updates itself from those releases. Live interop: `cargo test -p jcode-remote --test live_relay -- --ignored` against `DEV_LOGIN=1 go run ./cmd/jcrelay`.

**Updates (OTA)**: `tauri-plugin-updater` + `tauri-plugin-process` (relaunch). The app checks `releases/latest/download/latest.json` on GitHub (`plugins.updater` in `tauri.conf.json`, minisign `pubkey`) right after launch (1.5 s; an update found then opens the dialog) and every 6 h (only the update buttons light up) (`stores/updater.ts`, not in `vite dev`); a sidebar button, `components/UpdateButton.tsx` (top right of the Welcome page and the workspace title bar; a manual check that finds a release opens the dialog) and Settings → Updates open `components/UpdateDialog.tsx` (notes as plain text, progress, restart). The restart sends `ExitRequested` with `RESTART_EXIT_CODE`, which the quit confirmation lets through; `RunEvent::Exit` kills terminals and servers. Plain `tauri build` needs no key: only `scripts/release/build-macos.sh` / `build-linux-windows.sh` enable `createUpdaterArtifacts` via `--config` and need `TAURI_SIGNING_PRIVATE_KEY`; `latest-json.mjs` (verifies each signature; `--merge` adds platforms to a published feed) and `publish.sh` produce the feed and the release from the Mac, and the pushed tag runs `.github/workflows/release.yml`, which builds Linux/Windows natively with the `TAURI_SIGNING_PRIVATE_KEY` repo secret, signs the .deb/.rpm too (`tauri signer sign`; the updater picks `linux-x86_64-deb`/`-rpm`/`-appimage` by install type and refuses another format with "invalid updater binary format"), merges them into the release's `latest.json` and rewrites `SHA256SUMS` for all files; every release needs `bump-version.sh`. The private key never goes in the repo (see `docs/RELEASE.md`).

**Usage / context meter**: `Db::session_usage` + `get_session_usage` give per-session totals and the latest request's input tokens (≈ current context fill); `useChat().usage` is loaded on session select and updated from `chat://usage`. `ContextMeter` divides by the model's `context_window` (falling back to a per-model-name table, then an estimate from message length before the first report).

**Visual system** (`frontend/src/styles.css`): "field instrument" look. Use the `accent-*` (teal) and `neutral-*` (green-tinted graphite, incl. `neutral-850/925`) theme colors; never raw hex or Tailwind's indigo/violet. Fonts are bundled via @fontsource (CSP forbids CDNs): IBM Plex Sans (body), IBM Plex Mono (`font-mono`, labels/paths/numbers), Bricolage Grotesque (`font-display`, titles). Helpers: `.eyebrow` (mono uppercase micro-label), `.ticks` (corner marks on focused/selected surfaces), `.dot-grid` (empty canvases), `.stagger` + `--i` (entrance), `animate-rise`. Radii stay small (3–6px); no gradients, glows, or sparkle icons. Brand mark: `components/Logo.tsx`.

**Frontend layouts**: `useApp().layout` is `"chat"` (default, `ChatLayout`: sessions sidebar, full-width `ChatPanel variant="full"`, context panel with Changes/Files/Editor/Terminal/Git) or `"code"` (IDE layout in `WorkspacePage`, `ChatPanel variant="side"`), persisted in localStorage. Heavy panels (CodeMirror, xterm, git, secondary pages) are `React.lazy` loaded and kept mounted once visited so terminal PTYs survive tab switches. Subscribe to zustand stores with selectors (`useShallow`); streaming text lives in `StreamingBubble` only.

**Landing page** (`site/`): a static page (`index.html`, `src/site.css` with the app's tokens, `src/site.js` for the ID/EN switch, OS detection and download links from the GitHub releases API). `site/build.sh` compiles Tailwind and writes `site/dist/` (ignored), which is what gets uploaded. Keep its feature and security claims true to the app.

Runtime data lives in the OS app-data dir under `com.jenderalcode.desktop/` (`jenderalcode.db`, `checkpoints/`, `credentials.json`).
